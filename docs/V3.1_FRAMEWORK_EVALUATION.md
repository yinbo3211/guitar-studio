# 六弦工坊 V3.1 · 框架演进技术预研（F11）

> 性质：**预研草案，不落地**。本文不引入任何运行时依赖，不改变「零依赖」产品底线。
> 结论先说：**V3.1 不做框架迁移**。仅在明确出现「多用户 / 云同步 / 团队版」需求时才启动评估立项。

## 1. 现状底线

| 项 | 现状 |
| --- | --- |
| 前端 | 原生 ES Modules（`assets/js/core|modules|data|i18n` + `main.js` 单一入口） |
| 后端 | 零依赖 Node 内置模块（`dependencies` 为空） |
| 音频 | Tone.js 15（本地 vendor 优先，CDN 双回退，失败降级原生 Web Audio） |
| 数据 | 全部存 localStorage，麦克风音频仅本地处理，不上传 |
| 构建 | 无构建系统，`npm start` 单命令启动 |

## 2. 候选方案评估

### 2.1 Vue 3（管理后台 / 统计页场景）

| 维度 | 评估 |
| --- | --- |
| 收益 | 统计页图表、计划页任务列表等「状态密集 UI」的声明式写法可显著减少 DOM 操作代码；组件化利于页面复用 |
| 成本 | 引入构建系统（Vite）或 CDN 运行时；现有 9 个模块需逐个迁移；Service Worker 缓存清单与模块图需重配 |
| 风险 | 破坏「零构建、直接开目录即用」的部署体验；离线缓存与 file:// 提示逻辑需重做 |
| 工作量 | 估算 3-4 周（渐进式迁移，先统计页/计划页试点） |

### 2.2 NestJS（多用户云端同步场景）

| 维度 | 评估 |
| --- | --- |
| 收益 | 若未来需要账号体系、跨设备同步练习数据，NestJS 的模块化与依赖注入能显著降低后端复杂度 |
| 成本 | 完全重写后端；引入 npm 依赖树（与零依赖底线直接冲突）；部署方式、DDNS 与一键脚本全部要重做 |
| 风险 | **与隐私底线强冲突**：一旦练习数据上云，必须新增隐私合规（数据最小化、导出/删除、传输与存储加密）、鉴权与审计 |
| 工作量 | 估算 8-12 周（含数据迁移与合规改造） |

## 3. 数据层与隐私底线冲突分析（关键）

当前数据层是 **localStorage 单用户本地存储**，云同步方案需引入 PostgreSQL 等服务端存储，冲突点如下：

| 冲突点 | 说明 | 应对（若启动迁移） |
| --- | --- | --- |
| 隐私承诺 | 现有宣传口径为「麦克风不上传、练习数据只存本地」 | 云同步必须**显式可选**，默认关闭；首次开启需二次确认与隐私说明 |
| 数据最小化 | 云端只需练习统计与计划，不需要音频 | 只同步结构化数据（PracticeSession / Plan），录音与音频永不上云 |
| 同步边界 | 离线编辑与多人/多端编辑冲突 | 以「设备为写入主体 + 时间戳合并」的简单策略起步，避免引入 CRDT 复杂度 |
| 导出/删除 | GDPR/个人信息保护要求的导出与删除权 | F1 已具备 JSON/CSV 导出，需补齐「一键删除云端数据」接口 |
| 鉴权 | 后台现有 24h 会话 + 失败锁定机制 | 迁移后需升级为账号体系（密码哈希、找回流程、审计日志） |

**结论**：云同步不是技术问题，而是产品定位与隐私承诺问题。在用户明确要求「跨设备同步」之前，本地优先仍是更优解。

## 4. 触发条件（明确的启动门槛）

满足任一条件才启动框架迁移立项：

1. 出现**多用户账号**需求（团队版 / 教师端 / 课程作业）；
2. 出现**跨设备云同步**需求且用户接受上云的隐私折衷；
3. 单个页面交互复杂度持续上升，原生 DOM 维护成本超过框架引入成本（以统计页/计划页为观测点）。

未满足前，工程投入优先放在：测试分层补齐（单元/模块/集成/端到端）、乐理与统计能力深化、四语文案覆盖。

## 5. 不迁移时的替代改进（已在 V3.1 落地）

- 目录与分层已清晰（core / modules / data / i18n），框架带来的组织收益部分已被抵消；
- `music-spelling` / `practice-store` 等纯函数模块自带单测，可独立演进；
- 统一 lint（`scripts/lint.mjs`）与四语词条校验守护一致性。
